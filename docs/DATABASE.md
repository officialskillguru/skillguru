## 4. Row Level Security

RLS is enabled on all 78 tables. Status as of 2026-07-24 (previous findings in parentheses, all fixed this session unless noted):

### Security lints (from `get_advisors(type=security)`)
- ~~**1 ERROR**: `public.transactions` `SECURITY DEFINER` view~~ — **FIXED**: `ALTER VIEW public.transactions SET (security_invoker = true)`.
- ~~**3 WARN** — unrestricted `WITH CHECK (true)` INSERT policies on `login_history`, `payment_logs`, `webhooks`~~ — **FIXED**: restricted to `service_role` only.
- ~~**4 WARN** — `function_search_path_mutable`~~ — **FIXED** via `ALTER FUNCTION ... SET search_path`.
- **~24 WARN → ~22 WARN remaining** — `SECURITY DEFINER` Postgres functions callable by `anon`/`authenticated` via PostgREST RPC. Reviewed function-by-function: `calculate_profile_completion(profile_id uuid)` and `get_unread_notification_count(p_user_id uuid)` both took an arbitrary target-user argument with **no ownership check**, letting any caller (including anonymous, via Postgres's default `PUBLIC` grant) enumerate another user's profile-completion score or unread-notification count — neither is called from the frontend via RPC (confirmed by grep), so **fixed** by revoking `EXECUTE` from `PUBLIC`/`anon` (keeping `authenticated` on the former only because a trigger depends on it). The remaining ~22 (`get_current_identity`, `has_role`, `has_permission`, `handle_new_user`, `get_current_roles`/`permissions`, `get_course_id_for_lesson`/`module`, `global_search`, `has_active_enrollment`, `is_course_mentor`, `log_audit_event`, `create_default_notification_prefs`/`user_settings`, `recalculate_course_progress`, `current_user_permissions`) were reviewed and judged safe-by-design — none take an arbitrary foreign-user identifier without an internal `auth.uid()` check, or are legitimately meant to be called pre-auth (e.g. `handle_new_user`).
- **2 WARN** — extensions `unaccent` and `pg_trgm` installed in the `public` schema instead of a dedicated `extensions` schema (best practice, low severity). **Not fixed** — deferred; moving extension schemas requires requalifying every dependent index/function, low reward given pre-launch status.
- **1 WARN** — Leaked-password protection (HaveIBeenPwned check) disabled in Supabase Auth. **Not fixed via this pass** — this is an Auth *dashboard* setting (Authentication → Policies → Password Security), not reachable via SQL/migration or the available MCP tools. One-click manual step recommended before real launch.

### Performance lints (from `get_advisors(type=performance)`) — **~130 overlap groups RESOLVED 2026-07-24**
- ~~**732** `multiple_permissive_policies`~~ — this raw count double-counted per default Postgres role (anon/authenticated/authenticator/dashboard_user/etc. all separately enumerated for the same underlying overlap); the real issue was **~130 groups of genuinely overlapping permissive policies** across ~65 tables (e.g. `assignment_submissions` had both "Mentors grade submissions" and "Students manage own submissions" as separate permissive `UPDATE` policies). **Fixed**: every group consolidated into a single policy per table+command, condition = OR of the originals. Verified structurally (spot-checked several tables' `pg_policy` definitions match the expected union) and behaviorally (simulated a non-admin authenticated session, confirmed row visibility unchanged). Zero overlapping permissive-policy groups remain.
- ~~**86** `auth_rls_initplan`~~ — **FIXED** in the same pass: every rewritten policy now wraps `auth.uid()`/`auth.<fn>()` in `(select auth.<fn>())`.
- **104** `unused_index` / **75** `unindexed_foreign_keys` — informational only given near-zero current row counts; **not acted on** — revisit once real production query patterns emerge.

## 6h. AI Career Guidance (added 2026-07-27)

`20260727090000_career_guidance_reports.sql` + `supabase/functions/career-guidance/index.ts` - previously entirely greenfield for students (the public `GuidancePage.tsx` is an unrelated marketing lead-capture page, unrelated schema). Reuses the `AIProvider`/`GeminiProvider` abstraction (`supabase/functions/_shared`) built for the AI Voice Agent, and the same `GEMINI_API_KEY` Edge Function secret already configured for `converse` - no new credential, no duplicated LLM wiring.

New `career_guidance_reports` table: `student_id`, `target_role`, `summary`, `skill_gaps jsonb`, `recommended_course_ids uuid[]`, `action_items text[]`, `model_name`, token counts, `created_at`. Owner-only SELECT RLS (`student_id = auth.uid() OR has_role('admin')`) - **no INSERT/UPDATE/DELETE policy at all**; every row is written by the Edge Function's service-role client only, matching the RPC-only write pattern used elsewhere in this project for privileged operations.

The Edge Function (`verify_jwt: true`, caller-JWT client for `auth.getUser()` + service-role client for data, mirroring `book-mentor-session`'s exact structure) gathers only real, server-fetched context before calling Gemini - the student's actual Resume Builder content (experience/projects/certifications/achievements/education/skills/bio), real active enrollments, and a real published-course catalog (id/title only, capped at 60 rows). The model is asked for `responseSchema`-enforced structured JSON (summary, skill gaps with priority, recommended course IDs, action items). **Anti-hallucination guard**: after generation, `recommendedCourseIds` is intersected against the real catalog IDs fetched server-side - any ID the model invents is silently dropped before the report is ever saved or shown, mirroring `converse`'s existing "grounded claim with zero sources" override pattern.

Live-verified the RLS: the owning student sees their report, a different student sees zero rows, and a direct client-side `INSERT` is rejected (no policy permits it). **Not live-verified**: an actual authenticated end-to-end call to the deployed function (`career-guidance`, version 2, `ACTIVE`) - no test-user session was available in this tool environment to sign in as a real student and invoke it from a browser. The function was thoroughly code-reviewed and its schema/RLS dependencies were independently verified live; a real click-through is recommended before treating this as fully production-validated.

## 6g. Resume Builder (added 2026-07-27)

`20260727080000_resume_builder.sql` + `20260727080500_resume_builder_student_profile_upsert_rpc.sql` — previously entirely greenfield. Reuses existing columns rather than duplicating them: contact/links/summary live on `profiles` (`full_name`/`phone`/`city`/`state`/`country`/`linkedin_url`/`github_url`/`portfolio_url`/`website_url`/`bio` - all real columns that had no edit UI anywhere in the app before this feature), and education/skills live on `student_profiles` (`education`/`college`/`graduation_year`/`skills`). Only genuinely list-shaped, currently-absent sections got new tables: `resume_experience`, `resume_projects`, `resume_certifications`, `resume_achievements` - owner-scoped RLS (`student_id = auth.uid() OR has_role('admin')`, single `FOR ALL` policy per table since resumes aren't public), soft delete, `sort_order`, mirroring `mentor_experience`/`mentor_projects`/etc.'s exact shape.

**Real gap found and fixed via live verification**: `student_profiles` has an admin-only INSERT policy - identical, deliberate convention to `mentor_profiles` (both extension tables are meant to be provisioned by an admin/service path, not self-inserted). This meant a student who had never had a `student_profiles` row created for them could never save resume education/skills at all - a direct `.upsert()` from the client would fail on first use for most students. Fixed with `upsert_my_student_profile(p_education, p_college, p_graduation_year, p_skills)`, a SECURITY DEFINER RPC hardcoded to `auth.uid()` (no student-id parameter, so there is no impersonation surface), granted to `authenticated` only (explicitly revoked from `anon` up front - no repeat of the `get_mentor_available_slots`/placement-RPC anon-grant gap this time). Live-verified: a student can self-provision their `student_profiles` row through the RPC and manage every resume section; a different student sees zero rows across all four new tables and the `student_profiles` row itself.

PDF export is client-side via the browser's native print-to-PDF (`window.print()` plus a scoped `@media print` rule in `globals.css` that hides everything except `#resume-preview`) - not a new npm dependency. This keeps genuine, selectable text in the output (not a canvas screenshot) and avoids adding another large bundle to a build that already warns about >500kB chunks.

## 6f. Enterprise Placement Management System (added 2026-07-27)

`20260727073017_placement_module_schema.sql` (+ `..._revoke_anon.sql` follow-up) — the full Placement Module, previously entirely absent from the schema. Nine new tables:

- **`hiring_partners`** — companies. `partner_user_id uuid references profiles(id)` is nullable and unused today, reserved so a future hiring-partner login can be wired to an existing row without another migration.
- **`job_postings`** — `status` lifecycle `draft → open → closed/cancelled`; `eligibility_criteria jsonb` and `skills_required text[]` are intentionally free-form (no rigid eligibility-rule schema was specified).
- **`placement_applications`** — the pipeline: `applied → shortlisted → interview_round_1 → interview_round_2 → hr_round → selected → offer_released → joined`, with `rejected`/`withdrawn` reachable from most states. Unique `(job_posting_id, student_id)` - one application per student per posting.
- **`application_documents`** — resume overrides/cover letters/ID proof, referencing `files.id` (uploaded via the existing `storage.service.ts` pipeline into the `students` bucket, same as avatars).
- **`interview_rounds`** — scheduling reuses the existing **`meetings`** table (no new columns needed - `entity_type`/`entity_id`/`attendee_id` already existed from the mentor-booking feature); this table adds the round-number/type/decision layer meetings doesn't have.
- **`interview_feedback`** — interviewer notes, admin-internal only (never exposed to the student directly - only the resulting `interview_rounds.decision` is).
- **`placement_offers`** — one per application (`UNIQUE(application_id)`), `status` lifecycle `released → accepted/declined/revoked`.
- **`placement_status_history`** — insert-only audit trail of every stage transition, written by every RPC below.
- **`saved_placements`** — student "wishlist" for job postings, mirrors `public.wishlists`' shape exactly.

**Write path**: `placement_applications`/`interview_rounds`/`interview_feedback`/`placement_offers`/`placement_status_history` have **no direct INSERT/UPDATE RLS policy at all** - every state transition goes through a `SECURITY DEFINER` RPC (`apply_to_job`, `withdraw_application`, `advance_application_stage`, `schedule_interview_round`, `record_interview_feedback`, `release_offer`, `mark_placement_joined`), matching this project's established pattern for privileged, cross-cutting writes (`submit_quiz_attempt`, `reply_to_testimonial`). Each RPC validates ownership/role internally, writes the status-history row, and inserts a real student-facing notification via the existing `notifications` table. `application_documents` and `saved_placements` are plain owner-scoped RLS CRUD (no RPC needed - not privileged operations).

**Advisor fix**: the first migration pass left all 7 RPCs callable by `anon` (Postgres grants EXECUTE to PUBLIC by default at function creation, and `REVOKE ALL ... FROM PUBLIC` alone didn't strip it - same gap hit once before with `get_mentor_available_slots`). Fixed with an explicit `REVOKE ALL ... FROM anon` per function (`20260727073511_placement_module_revoke_anon.sql`), then folded into the schema migration file on disk so a fresh clone lands in the same end state.

**Deliberately not built as new tables**: `public.organizations` was considered for hiring partners and rejected - it models multi-tenant *platform* clients (SkillGuru's own enterprise customers), a different concept from companies that hire students. Hiring-partner login was designed for (`partner_user_id`) but not implemented, per explicit direction.

Live-verified the full pipeline in one rolled-back transaction: a student applies (duplicate application correctly rejected), an admin shortlists → schedules an interview round → records feedback → marks selected → releases an offer → marks joined - confirming the owning student sees every row (application, interview round, the underlying `meetings` row, offer, 6-entry status history) while a different student sees zero rows at every stage and a non-admin caller is rejected from every admin-only RPC. Zero residual data (rolled back).

## 6b. Mentor account lifecycle (added 2026-07-27)
