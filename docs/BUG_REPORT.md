# SkillGuru — Bug Report

_Last analyzed: 2026-07-24. Severity is about user/business impact, not code elegance._

## Found and fixed 2026-07-29

- **BUG-44** (HIGH, latent since 2026-07-18): `log_audit_event()` RPC (`20260718000005_enterprise_features.sql`) inserts into an `audit_logs.details` column that never actually existed on the live table. Every call has been failing with `42703` since the function was written — undetected because nothing called it in the ~11 days since, until Enterprise Mentor Management Phase 1 exercised it live for the first time (discovered via a real edge-function test against production, not by reading the code). Meanwhile 4 separate code paths (`create-mentor`, `useAdminMutations.ts`'s local `logAudit()`, and now the fixed callers) had been writing `audit_logs` directly instead, bypassing the RPC entirely — so audit logging was never actually broken end-to-end, just this one RPC was dead on arrival. Fixed with an additive `ALTER TABLE audit_logs ADD COLUMN details jsonb` migration; verified live (lock/unlock/force-logout/course-reassign all now record correctly with old/new values).
- **BUG-45** (HIGH, latent since `notificationsService` was written): `notifications` table has only a "Users view own notifications" SELECT policy (`recipient_id = auth.uid()`) — no admin SELECT policy ever existed. Postgres RLS requires an `INSERT ... RETURNING` to also satisfy the table's SELECT policy for the returned row, and `notificationsService.sendNotification()` (the one and only send path — used for task-assignment, meeting-scheduling, bulk-notify, and broadcast notifications) always does `.insert().select().single()`. Since the recipient is virtually never the admin themselves, **every admin-initiated notification to another user has been silently failing with `42501` for the entire time this function has existed** — confirmed via a real `curl` request against production with `Prefer: return=representation` (fails) vs. without it (succeeds with 201), isolating the exact cause. Not caught earlier because nothing had exercised this path end-to-end against production before Enterprise Mentor Management Phase 3's live verification pass. Fixed via an additive `ALTER POLICY` widening the SELECT policy to also allow `has_role('admin') OR has_role('super_admin')`; re-verified live (insert-with-representation now returns 201 with the full row).
- **BUG-46** (CRITICAL, latent since Phase 1.19, 2026-07-27): `profiles` RLS has only ever allowed `auth.uid() = id OR has_role('admin')` for SELECT — there was never a public policy. Every public-facing mentor query (`mentor.repository.ts`'s `findBySlug`/`findRelated`, and the new `listCatalog`) joined `profiles` directly for `full_name` — meaning **the "real, DB-backed" public mentor profile page has been showing "Mentor Not Found" (or a blank catalog) for every genuine anonymous visitor and every non-admin authenticated user since Phase 1.19 shipped** — the exact audience the page exists for. Verification at the time happened in an admin session, which silently worked and masked the gap; only a live logged-out-browser test in Phase 3 caught it. Fixed with a narrow `get_public_mentor_profiles(uuid[])` SECURITY DEFINER RPC exposing only `id/full_name/city/country` for genuinely active mentors — not a blanket `profiles` RLS widening, which would have leaked email/phone/DOB/address to the public. Re-verified live: signed out of the app entirely, reloaded `/mentors` and `/mentors/:slug`, confirmed real mentor names render and zero console errors.
- **BUG-47** (MEDIUM, same root cause as BUG-46): `enrollments` correctly has no public SELECT policy (private student data — that part is by design), but the public mentor catalog/profile pages queried it directly for "Students Mentored" counts, so that stat silently read 0 for every anonymous visitor regardless of real enrollment data. Fixed with two aggregate-only RPCs (`get_public_mentor_student_counts`, `get_public_course_enrollment_counts`) that return counts only, never individual enrollment/student rows.
- **BUG-48** (MEDIUM, latent since Phase 1.20): `get_mentor_available_slots()` was never granted `EXECUTE` to the `anon` role — confirmed via a live logged-out browser session, console showed real `401` errors on `/rest/v1/rpc/get_mentor_available_slots`, meaning the public mentor profile page's booking widget has been unable to show availability to any real anonymous visitor since it was built (the "No upcoming availability" message they saw was a permissions error, not real data). Fixed with a one-line `GRANT EXECUTE ... TO anon` — the function is `SECURITY DEFINER` and only computes open time slots, no PII.

## Critical

### BUG-01: Public lead-capture forms are broken against the live schema — **RESOLVED 2026-07-24**
`supabase/functions/leads/index.ts` inserts `full_name`, `source`, `course_slug`, `message` into the `leads` table. The live `leads` table (`supabase/migrations/20260718000001_crm_schema.sql`) has `name`, `source_id` (FK), `course_interest_id` (FK), `budget`, etc. — **none of the columns the function writes exist**. This function is called live by `src/services/leads.ts` from the public Contact/Enquiry/Counselling/Demo forms. **Any visitor submitting these forms today will hit a runtime error** (or silently fail, depending on how the frontend handles the Edge Function error response) instead of creating a lead.
- **Impact**: loses inbound leads/signups from the marketing site — a direct revenue/growth impact, not just an internal tooling gap.
- **Fix applied**: rewrote the function against the real schema (`name`/`source_id`/`course_interest_id`/`notes`/`tags`, resolving lead-source and course-slug lookups server-side), redeployed with `verify_jwt: false` (it's a public anonymous endpoint), and live-tested two real submissions (`contact` and `enquiry` types) against production — both created correct rows with resolved foreign keys, then cleaned up.

### BUG-02: Entire Razorpay payment pipeline is disconnected from the real backend — **RESOLVED 2026-07-24**
Three separate breaks compounded into "payments don't really work": (1) the frontend called Edge Functions by names that didn't exist (`create-razorpay-order` etc. vs the real `create-order`/`verify-payment`/`refund-payment`); (2) every checkout therefore fell through to a **client-side "dev fallback"** that inserted a `payments` row with `amount: 0` and granted enrollment directly from the browser — no real payment, no signature verification, no admin-in-the-loop; (3) even the correctly-named functions weren't deployed at all (`list_edge_functions` showed only `create-mentor` live) and targeted a nonexistent `student_enrollments` table.
- **Fix applied**: see `docs/PAYMENT_ARCHITECTURE.md` for the full design. Built a `PaymentProvider` abstraction (`MockPaymentProvider`/`RazorpayProvider` behind a common interface, resolved once server-side via `PAYMENT_PROVIDER` env var) and rewrote all five payment Edge Functions (`create-order`, `verify-payment`, `refund-payment`, `payment-status`, `payment-webhook`) against the real schema; deployed all five (previously zero were live). Rewrote the frontend `payment.service.ts`/`usePayment.ts` to call these by their real names and **removed the client-side dev-fallback entirely** — there is no code path left that can grant enrollment or record a payment from the browser without going through a service-role Edge Function. Live-verified: all four JWT-gated functions correctly reject unauthenticated calls; `payment-webhook`'s HMAC signature verification accepts a correctly-signed payload and rejects/logs an unmatched order, confirmed via a live curl round-trip against the deployed function and a `webhooks` table read.

### BUG-03: Payment Edge Functions wrote columns that don't match the live `notifications`/`enrollments` schema — **RESOLVED 2026-07-24**
The draft `verify-payment`/`payment-webhook` inserted into `notifications` using `user_id`/`message`/`type`/`category`/`status` — none of which are the real columns. The actual live schema (confirmed by reading `notifications.service.ts`'s own real, working insert calls) is `recipient_id`/`title`/`message`/`type`/`is_read`, with any category-like grouping living inside the `metadata` jsonb column, not a top-level `category`/`status` column as previously assumed here. Also found and fixed while rewriting: both draft functions inserted into `invoices` with `user_id`/`amount`/`status` columns that don't exist on that table (it only has `order_id`/`invoice_number`/`pdf_url`), and `payment-status`/`refund-payment` both called a nonexistent RPC (`current_user_roles`; the real one, used everywhere else in the codebase, is `get_current_roles`).
- **Fix applied**: all three issues fixed in the same rewrite as BUG-02 — every insert now matches the live schema exactly, verified against `pg_indexes`/`information_schema.columns` reads rather than assumed.

### BUG-04: `public.transactions` view is `SECURITY DEFINER` — **RESOLVED 2026-07-24**
Flagged by Supabase's security advisor as an ERROR-level finding: the view runs with the permissions of its creator rather than the querying user, which can bypass RLS for whoever is granted access to the view.
- **Impact**: potential unauthorized data exposure/mutation via the view, depending on what it selects from and what grants exist on it.
- **Fix applied**: `ALTER VIEW public.transactions SET (security_invoker = true);` — the view now respects the querying user's own RLS instead of the creator's.

## High

### BUG-05: Refunds were a hardcoded mock regardless of provider — **RESOLVED 2026-07-24**
The old `refund-payment/index.ts` never called the Razorpay refund API at all — its own code comments said "Mock refund for now" unconditionally, even when nominally configured for real payments.
- **Fix applied**: `refund-payment` now delegates to whichever `PaymentProvider` is active. `verify-payment` now populates `payments.razorpay_payment_id` at verification time (the exact gap the old code's own comments identified), so `refund-payment` can look it up and pass it to the provider's `refund()` method. `MockPaymentProvider.refund()` deliberately still simulates (by design, until real Razorpay credentials exist — see PAYMENT_ARCHITECTURE.md §11); `RazorpayProvider.refund()` calls the real Refunds API and is only exercised once `PAYMENT_PROVIDER=razorpay` is set.

### BUG-06: Mentor status toggle silently corrupts mentor bio instead of changing status — **RESOLVED 2026-07-27**
`mentors.service.ts`'s `setMentorStatus()` was implemented as `updateMentor(id, { bio: "status change attempted" })` — clicking "suspend"/"activate" on a mentor in the admin UI **overwrote that mentor's bio field** with a placeholder string instead of changing any status flag. There was also no soft-delete/restore capability at all for mentor accounts, despite Admin needing "Delete"/"Restore" controls.
- **Impact**: destructive data loss (a mentor's real bio was silently replaced) disguised as a status-toggle action; no real way to suspend or remove a mentor account existed.
- **Fix applied**: migration `20260727000003_mentor_status_lifecycle.sql` adds a real `status` (`'active'|'suspended'`, CHECK-constrained) and `deleted_at` column to `mentor_profiles` — additive, backward-compatible (existing rows default to `active`/`NULL`, identical to prior implicit behavior). Tightened the `consolidated_select` RLS policy (previously `has_role('admin') OR true` — i.e. always true) to `has_role('admin') OR deleted_at IS NULL`, so a soft-deleted mentor is no longer publicly visible while admins retain full visibility. Rewrote `mentors.service.ts`: `setMentorStatus()` now genuinely updates `status`; new `softDeleteMentor()`/`restoreMentor()` replace the old irreversible hard `deleteMentor()` (removed — hard-deleting would cascade-delete the mentor's courses/history and make "Restore" impossible, the wrong behavior for an EdTech platform with enrolled students). Deleted the fully-dead duplicate `src/repositories/mentors.repository.ts` (`MentorsRepository`, zero importers — its own `updateMentorStatus()` was a `fail(new UnexpectedError("status field unsupported"))` stub, the same underlying gap this bug fixes). Wired real Suspend/Reactivate, Delete, and Restore controls into `AdminMentorsPage.tsx` (row actions + drawer Danger Zone), plus a status/deleted filter on the mentor list. **Real enforcement, not just a cosmetic flag**: `MentorProtectedRoute` now checks the mentor's live `status`/`deleted_at` (via a new `useMentorAccountStatus()` hook) and blocks a suspended or deleted mentor from the Mentor Dashboard with a real "Account Suspended/Removed" screen — admins bypass this check for their own access. Live-verified: a soft-deleted mentor is confirmed invisible to a simulated non-admin RLS session (rolled back, zero residual data).

### BUG-07: Admin Dashboard displays entirely fabricated metrics — **RESOLVED 2026-07-24**
Every widget on `AdminDashboardPage` (`DashboardStats`, `PlatformOverviewWidget`, `SystemHealthWidget`, `RecentMentorsWidget`, `RecentOrdersWidget`, `TopCoursesWidget`, `RecentActivitiesWidget`, `RoleManagementWidget`) rendered hardcoded arrays (e.g. "5,482 students," "₹14,82,000 revenue," every system marked "Online"/"Healthy" including the Payment Gateway) rather than calling any real hook/service. - **Impact**: the primary landing page for admins showed numbers with no relationship to the real database — a serious trust/decision-making risk if anyone acted on these figures.
- **Fix applied**: rewired all 8 widgets (`QuickActionsWidget`'s navigation was already real, left untouched) to `useDashboardData()`, `useMentors()`, `analyticsService.getTopCourses()`, and direct real queries. `SystemHealthWidget` now does a lightweight real check (DB reachability, live storage bucket count, active payment provider) linking to the already-real `AdminSystemHealthPage`.

### BUG-08: `dashboard.service.ts` fabricated revenue and placement-rate figures — **RESOLVED 2026-07-24**
`getDashboardChartData()` hardcoded ₹15,000 mock revenue per enrollment and injected `Math.random()` into the placement-rate figure on every call (comment: "Smooth out placement rate for aesthetics"). `totalLeads` was hardcoded to 0 despite a real, populated `leads` table existing.

### BUG-19: `has_permission()` referenced a nonexistent column, silently blocking all course/module/lesson/resource writes — **RESOLVED 2026-07-24**
The SQL function `public.has_permission(_permission_code text)` filtered on `p.code`, but the real `permissions` table column is `p.slug`. Every RLS policy gating course/module/lesson/resource INSERT/UPDATE that calls `has_permission(...)` therefore threw `ERROR: 42703: column p.code does not exist` on every write attempt — for mentors **and** admins alike, since neither role had an unconditional bypass on these tables' write policies.
- **Impact**: course/module/lesson/resource creation and editing was completely broken platform-wide, for every role, with no clear error surfaced to the end user beyond a generic Supabase error.
- **Fix applied**: corrected the column reference to `p.slug`; verified via live RLS simulation (`set local role authenticated; set local request.jwt.claims`) that admin can update any course and mentors can update only their own.
- **Compounding cause, also fixed**: the `courses.create`/`courses.update_own`/`courses.update_all` permission rows didn't exist in `permissions` at all, and `role_permissions` was empty — so even with `has_permission()` fixed, no role actually held these permissions. Seeded the missing rows and granted them to mentor (`create`, `update_own`) and admin (all three).

### BUG-23: `enrollments` has no student-facing INSERT policy — students cannot self-enroll in anything, including free courses

### BUG-42: Lesson video/PDF uploads were foldered by `moduleId`, but the storage RLS policy expects the course, so no enrolled student (or even the owning mentor) could ever read them back — **RESOLVED 2026-07-27**
Found while wiring up real video playback. `storage.objects`' `courses` bucket has a real, properly-scoped RLS SELECT policy: `has_role('admin') OR is_course_mentor((storage.foldername(name))[1]::uuid) OR has_active_enrollment((storage.foldername(name))[1]::uuid)` — i.e. it checks enrollment/mentorship against the **first folder segment**, expecting it to be the course's ID. But `CourseCurriculumEditor.tsx`'s lesson upload call was `uploadFile("courses", file, moduleId)` — foldered by the **module's** ID instead. Since a module ID never equals any real course ID, `has_active_enrollment(moduleId)`/`is_course_mentor(moduleId)` always evaluated false for real users — every lesson video/PDF was silently unreadable by anyone except admins, regardless of enrollment. This is why the video player was left as a `<p>Video Player (Mock)</p>` placeholder in the first place: wiring up real playback against this path would have failed with a silent 403 for every real student.
- **Impact**: core "continue learning" functionality was structurally broken at the storage layer, invisible until someone actually tried to read a file back (uploads themselves succeeded, masking the bug).
- **Fix applied**: threaded `courseId` down through `CourseCurriculumEditor` → `ModuleEditor` → `LessonForm` and changed the upload call to `uploadFile("courses", file, courseId)`, matching the RLS policy's actual expectation (confirmed by reading `has_active_enrollment(p_course_id uuid)`'s real definition). `AdminCoursesPage.tsx`'s separate thumbnail upload already used `courseId` correctly.

### BUG-47: Quiz/mock-test system had zero real UI on either side, a broken lesson linkage, and a real answer-key leak — **RESOLVED 2026-07-27**
`quiz.service.ts`/`useQuiz.ts`/`quiz.repository.ts` had **zero UI consumers anywhere** despite a substantial real schema (`quizzes`/`quiz_questions`/`quiz_options`/`quiz_attempts`/`quiz_answers`) and `lessons.content_type` already offering `"quiz"` as an authorable lesson type — a mentor could label a lesson "Quiz" but had no way to add questions, and a student had no way to take it. Investigating turned up three separate real defects:
1. `quizRepository.getQuizByLessonId()` queried `quizzes.module_id` with a comment admitting *"schema change: quizzes are linked to modules, not lessons"* — the lookup could never match a real per-lesson quiz.
2. `useQuiz.ts`'s `startAttempt` passed the raw student/user ID where `quiz_attempts.enrollment_id` (a foreign key to `enrollments.id`) was required — every real attempt would have failed with a type/constraint error.
3. **Security**: `quiz_questions`/`quiz_options` RLS SELECT policies allowed **any authenticated user** (not just students enrolled in the course) to read a published quiz's questions **and options — including `quiz_options.is_correct`, the answer key** — before ever attempting it.
- **Impact**: the entire feature was unusable end-to-end, and the underlying data model additionally leaked graded-assessment answers to any signed-in user, enrolled or not.
- **Fix applied**: migration `20260727000005_quiz_lesson_link_and_secure_scoring.sql` adds a real `quizzes.lesson_id` column, tightens the three SELECT policies to require `has_active_enrollment()` (or mentor/admin ownership), and adds a `submit_quiz_attempt()` SECURITY DEFINER RPC that validates the caller owns the enrollment, computes the score server-side from the real answer key, and writes the attempt + answers atomically — the answer key never round-trips through the client during a live attempt (mirrors the `reply_to_testimonial`/`book-mentor-session` pattern already used elsewhere). New `quiz-authoring.service.ts` (mentor CRUD for questions/options, MCQ and true/false only — multi_select/short_answer aren't exposed since no auto-grader exists for them, an honest scope limit rather than half-finished UI) wired into `CourseCurriculumEditor.tsx` as a real "Manage Quiz" panel. Live-verified: correct-answer scoring (100%, passed), the answer-key leak fully closed (a non-enrolled user reads 0 rows from `quiz_options`), and enrollment impersonation rejected (`P0001: Not authorized to submit this attempt`) — all three cycles rolled back, zero residual data. One further bug caught by this same live-verification process before landing: the RPC's first draft referenced a nonexistent `quiz_attempts.completed_at` column (real columns are `started_at`/`submitted_at` only) — fixed and re-verified.
