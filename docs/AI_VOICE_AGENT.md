# AI Voice Sales Agent — Architecture & Build Plan

_Started 2026-07-25. This supersedes the "not scheduled" note in `DEVELOPMENT_ROADMAP.md`'s Vision 2026 section — this is now an active, in-progress build, tracked here rather than as a single aspirational bullet._

## Why this document exists

The original ask for this feature was a full enterprise voice AI platform — RAG, n8n orchestration across 15+ workflows, streaming voice, payments, calendar booking, SMS, analytics, a security program — as a single deliverable. That's a genuine multi-month, multi-engineer build. Building all of it at once, with most of the required infrastructure (n8n instance, payment provider, Google Calendar, JWT/encryption keys) not yet provisioned, would produce exactly the kind of disconnected, non-functional scaffolding this project spent Phases 1.12–1.18 removing. This doc exists so the build proceeds in real, working, verified increments instead.

**Security note**: real-looking API keys/secrets were pasted directly into the chat that kicked this off (Gemini, ElevenLabs, Twilio, Gmail app password). None of those values were written to any file in this repo. If they haven't been rotated yet, rotate them now (Google AI Studio, ElevenLabs dashboard, Twilio console, Google App Passwords) — anything pasted into a chat should be treated as compromised.

## What Phase 2.1 actually built

### Reused (not duplicated)
- **Leads/CRM**: `crm.service.ts` and the existing `leads`/`lead_activities`/`pipeline_*` tables remain the single source of truth for lead data. Phase 2.1 only *extends* `leads` with qualification columns (see below) — it does not create a parallel leads table.
- **Notifications**: outbound email/in-app notifications will go through the existing `notifications.service.ts`, not a new notification path.
- **Appointments**: will reuse the existing polymorphic `meetings` table (`entity_type`/`entity_id`) rather than a new `appointments` table.
- **Files/storage**: `agent_messages.audio_file_id` references the existing `files` table (same pattern as avatars/lesson videos), not a new storage mechanism.
- **Audit trail**: business-level actions still go through `audit_logs`; `agent_logs` (new) is specifically for agent-internal pipeline observability (API calls, retries, failures) so it doesn't pollute the business audit trail.

### New (migrations `20260725000001`, `20260725000002`)
- `agent_conversations` — one row per voice/chat session. `visitor_id` (client-generated UUID) identifies anonymous visitors before any lead/profile exists; `profile_id`/`lead_id` populate once identity/lead capture happens mid-conversation.
- `agent_messages` — one row per conversational turn (`role`, `content`, `audio_file_id`, `intent`, `function_call`, `citations`, `tokens_used`, `latency_ms`).
- `agent_knowledge_documents` + `agent_knowledge_chunks` — the RAG corpus. Documents can optionally point at `source_table`/`source_id` (e.g. a real `courses.id`) for incremental re-sync from existing data, or be manually authored. Chunks carry a `vector(768)` embedding (Gemini `text-embedding-004` dimensionality) with an HNSW cosine-similarity index.
- `agent_customer_memory` — one row per profile: preferred courses, freeform preferences, a running interaction summary, and conversation counters.
- `agent_logs` — structured internal pipeline logs, separate from `audit_logs`.
- `leads` extended with: `city`, `country`, `education`, `experience_years`, `career_goal`, `timeline`, `learning_mode`, `urgency`, `lead_score` (0–100), `agent_conversation_id`. All nullable/additive — zero impact on the existing CRM UI.
- `match_agent_knowledge(query_embedding, match_count, similarity_threshold, filter_category)` — a real, callable RPC (`supabase.rpc('match_agent_knowledge', {...})`) doing cosine-similarity search over the corpus, returning parent document title/category for citation display.

### RLS
Every new table has RLS enabled. Pattern: admins (`has_role('admin')`) have full access; a signed-in customer can `SELECT` their own conversations/messages/memory; anonymous visitors have **no direct table access** — the public site talks to the agent exclusively through an edge function / n8n webhook using the service role, not directly against these tables. Knowledge documents/chunks are additionally readable by anyone once `is_active = true`. Policies were written once, then immediately consolidated (single policy per action, `(select auth.uid())`/`(select has_role(...))` wrapping) to avoid the exact per-row-re-evaluation performance debt this project already paid down once in its Phase 0.7 RLS pass — see `mcp__supabase__get_advisors` output from 2026-07-25 for the before/after.

### Verified
- Migration applied live (`thhivnrxthsvoxftblwg`), tables confirmed present via `information_schema.tables`.
- Security/performance advisors re-run post-migration: only pre-existing/already-accepted warning categories, plus the RLS-initplan findings on the new tables specifically, which were fixed immediately (not left as new debt).
- `database.types.ts` regenerated from the live schema; `tsc --noEmit` clean.
- Full verification suite green: `tsc --noEmit`, `eslint .` (0 errors), `vitest run` (18/18), `npm run build`.

## What Phase 2.2 actually built

- **`supabase/functions/sync-knowledge-base/index.ts`** (deployed, `verify_jwt: false` — it does its own admin-role check via `get_current_roles()`, matching the `create-mentor` pattern). Callable as `POST /functions/v1/sync-knowledge-base` with an optional `{ sources: ["courses"|"mentors"|"testimonials"] }` body (defaults to all three). For each real row it: builds a plain-text document (course title/description/level/duration/price/mentor name; mentor headline/bio/expertise/experience; approved testimonial content/rating/course/student), `upsert`s it into `agent_knowledge_documents` keyed on `(source_table, source_id)`, deletes and re-chunks its `agent_knowledge_chunks`, and calls the real Gemini `text-embedding-004` REST API per chunk. Writes a summary row to `agent_logs` on every run (`event_type: 'knowledge_sync'`) and returns per-document errors individually rather than failing the whole batch if one row has bad data.
- **`agent_knowledge_documents_source_unique`** constraint (migration `20260726000001`) — added so the sync can genuinely `upsert` (onConflict) instead of relying on app-level check-then-write logic, which the `create-mentor` incident (BUG-40) already proved is unsafe under concurrent/retried calls.
- **`src/services/knowledge-base.service.ts`** + **`src/hooks/admin/useKnowledgeBase.ts`** — real service/hook layer: list documents, corpus stats (document/chunk counts, per-category breakdown), toggle a document's `is_active`, and invoke the sync function.
- **`src/pages/AdminKnowledgeBasePage.tsx`** — new admin page (`/admin/knowledge-base`, nav item under "SYSTEM") to trigger a sync, see live stats, see per-document sync errors inline, search documents, and toggle individual documents active/inactive without needing a re-sync.
- Verified: current real data is thin (2 courses — both `"E2E Course"` test fixtures with null descriptions — 3 mentor profiles, 0 approved testimonials), so the corpus will be small and test-fixture-flavored until real course/mentor/testimonial content exists. The pipeline itself is real and correct regardless of how much real content currently exists to feed it.

## What Phase 2.3 actually built

All logic lives in `supabase/functions/_shared/` (shared between the Deno edge runtime and, where the file has no Deno-specific globals, directly unit-testable under Vitest) plus the orchestrator itself at `supabase/functions/converse/index.ts`.

- **`ai-provider-types.ts`** — the `AIProvider` interface (`generateStructured()`, `embed()`), mirroring the existing `PaymentProvider` pattern (`MockPaymentProvider`/`RazorpayProvider` behind one interface). `ChatMessage`, `ToolDefinition`/`ToolCall`, `StructuredGenerationRequest`/`Result`.
- **`gemini-provider.ts`** — the only file that knows Gemini's REST shape (`gemini-2.5-flash` for generation, `text-embedding-004` for embeddings, same model already used by `sync-knowledge-base`). Function calling via `tools.functionDeclarations`, forced JSON via `responseMimeType`/`responseSchema`, 4-category safety settings, `AbortController` timeout + exponential-backoff retry (429/5xx/network only, never on 4xx).
- **`ai-provider-factory.ts`** — `createAIProvider("gemini", apiKey, model)`, with an exhaustiveness check so a new `SupportedProvider` variant without a matching case is a compile error.
- **`prompt-manager.ts`** — versioned (`PROMPT_VERSION = "2.3.0"`) system-prompt composer: persona + hard anti-hallucination/anti-injection rules, per-state guidance (14 states), voice-vs-chat channel notes, knowledge-context injection (with similarity scores), customer-memory injection.
- **`conversation-state.ts`** — the 14-state machine (`greeting` → ... → `conversation_end`, plus `recovery`/`fallback`/`human_escalation`). Stored in `agent_conversations.metadata.conversationState` (jsonb), not a new column/enum, so new states don't need a migration. `nextStateOrFallback()` never blindly trusts the model's self-reported next state — an unrecognized value falls back to `"fallback"`; a real-but-undocumented transition is kept but flagged (`wasUnexpected: true`) for logging.
- **`intent-schema.ts`** — 16 intents, 16 extracted-entity fields, and `AGENT_TURN_RESPONSE_SCHEMA` — the exact JSON Schema handed to Gemini's `responseSchema` for the final structured-output pass.
- **`lead-scoring.ts`** — pure, deterministic `scoreLead()` (contact info, budget stated, timeline urgency, profile completeness, conversation-state weight, intent-signal weight, engagement — capped 0–100, `low`/`medium`/`high` urgency). Intentionally not an LLM call: "a lead score that changes for reasons nobody can explain is worse than no score at all."
- **`tools.ts`** — the generic tool-calling framework. Four real tools this phase: `knowledge_search` (calls `match_agent_knowledge()` — the actual Phase 2.1 RAG RPC), `create_lead`/`update_lead` (real `leads`/`lead_activities` writes, tagged `ai_agent_created`/`ai_agent_updated` to distinguish from human CRM actions), `escalate_to_human` (real `support_tickets` insert, `category: 'ai_escalation'`, reusing the existing table rather than a new one). Calendar/payment/SMS/email tools are deliberately deferred to Phase 2.4+ (no connected provider yet) — not stubbed out as fake handlers.
- **`rate-limiter.ts`** — DB-backed (not in-memory — edge function instances are ephemeral/multiplied), 20 user messages/60s per `visitor_id`, checked against real `agent_messages` rows.
- **`pii-safe-logging.ts`** — regex email/phone masking for anything written to `agent_logs`/console (lead data itself is stored unmasked in `leads`, by design); a prompt-injection *detection* heuristic (flags and logs, never silently blocks a turn — the system prompt itself instructs the model to decline injection attempts gracefully).
- **`supabase/functions/converse/index.ts`** — the orchestrator. Flow per turn: rate-limit check → injection-detection (log-only) → load-or-create `agent_conversations` row (visitor-ownership checked to prevent conversation hijacking) → load short-term memory (last 20 `agent_messages`) + long-term memory (`agent_customer_memory` + resolved preferred-course titles) → persist the user's turn → **tool-calling pass** (up to 3 rounds, `TOOL_DEFINITIONS` offered, results fed back as `role: "function"` messages) → **structured-output pass** (no tools, `AGENT_TURN_RESPONSE_SCHEMA` forced) → grounding safeguard (if the model claims `groundedInKnowledge: true` with zero actual retrieved sources, the response is overridden with an honest "I don't have confirmed details" message and the turn is flagged `hallucinationRiskFlagged`) → lead scoring → persist assistant message + updated conversation state/entities + `agent_logs` row → return one fully-typed response (`detectedIntent`, `allIntents`, `confidence`, `conversationState`, `leadScore`, `extractedEntities`, `toolCalls`, `knowledgeSourcesUsed`, `suggestedNextAction`, `userFacingResponse`, `internalMetadata` with request id/prompt version/latency/token usage/risk flags).
- **Why two Gemini passes per turn**: Gemini doesn't cleanly support function-calling and a forced JSON response schema in the same call, so tool use (pass 1, tools enabled, free-form text) and structured intent/entity/state extraction (pass 2, schema-forced, no tools) are split. Knowledge retrieved during pass 1 is re-injected into pass 2's system prompt so the final grounded answer can cite it.
- **Tests**: 45 Vitest unit tests across 7 files in `supabase/functions/_shared/*.test.ts` (lead scoring, state machine, prompt manager, PII masking/injection detection, Gemini provider retry/timeout/parsing via a stubbed `fetch`, tool execution via a chainable Supabase-query mock, rate limiter). `vitest.config.ts`'s exclude list was narrowed so these actually run under `npm run test` (previously blanket-excluded all of `supabase/functions/**`).
- **Deployed**: `converse` Edge Function, project `thhivnrxthsvoxftblwg`, `verify_jwt: false` (it does its own Zod validation + DB-backed rate limiting — this endpoint must be callable by anonymous website visitors, same rationale as the rate limiter). Live-smoke-tested via a direct HTTP call — returns a clean, correctly-typed `MISSING_PROVIDER_KEY` response (see below), confirming all imports resolved and the deployment bundle is healthy.

## Live end-to-end verification (2026-07-26)

`GEMINI_API_KEY` was set as an Edge Function secret and `converse` was exercised with real HTTP calls against the live deployment. Two real model-availability breaks were found and fixed during this pass (both were Google-side deprecations, not bugs in this codebase):

- **`gemini-2.5-flash` returned 404** ("no longer available to new users"). Fixed by switching to `gemini-flash-latest` (a forward-compatible alias, set via the `GEMINI_MODEL` secret so no redeploy is needed if Google rotates the underlying model again) in both the `GEMINI_MODEL` secret and the code's own default fallback.
- **`text-embedding-004` returned 404** ("not found... or not supported for embedContent"). Fixed by switching to `gemini-embedding-001` with an explicit `outputDimensionality: 768` parameter, in both `gemini-provider.ts` (`converse`'s `embed()`) and `sync-knowledge-base/index.ts` — preserving the exact 768-dim vector shape the `agent_knowledge_chunks` pgvector HNSW index was built for. Verified the new model returns exactly 768 values before redeploying either function.

**Real conversation turns verified against the live function** (not mocked): greeting, course inquiry, pricing question, and a prompt-injection attempt. All four behaved correctly — intent detection, entity extraction, conversation-state transitions, lead scoring, tool execution (`knowledge_search` genuinely called `match_agent_knowledge()`), structured output, and `agent_logs`/`agent_messages` persistence with real (not fabricated) latency/token/prompt-version values were all confirmed via direct DB queries after the calls. The injection attempt was declined without acknowledging or repeating it, exactly per the system prompt's rule — the model returned to a neutral greeting instead of leaking any instructions.

**RAG correctness confirmed the hard way**: the corpus is currently empty (`agent_knowledge_documents`/`agent_knowledge_chunks` both at 0 rows — `sync-knowledge-base` was never successfully run before this pass, since `GEMINI_API_KEY` wasn't set until now, and the embedding model was also broken until the fix above). On the course-inquiry and pricing turns, the model correctly called `knowledge_search` (up to the 3-round cap), got empty results back every time, and — per the grounding rule — **refused to guess** at course names or prices, instead offering to connect the visitor with the team. This is the anti-hallucination safeguard working exactly as designed under the worst-case input (zero real knowledge to ground on), not a failure.

**Real production blocker found**: this API key is on Google's **free tier with a 5-requests-per-minute quota** on the resolved model. Each conversation turn costs 2-4 Gemini calls (tool-calling round(s) + the final structured-output pass), so the key exhausts its quota after roughly one turn and needs ~60s to recover — confirmed directly via a `429 RESOURCE_EXHAUSTED` response mid-testing. This key is **not usable for real multi-visitor production traffic** in its current tier. Remaining test scenarios (mentor info, FAQ, unknown question, lead qualification, human escalation, multi-turn continuity, full RAG-grounded citation verification) were not run in this pass — burning through them one-by-one at 5 RPM would take many more minutes per scenario and does not change the verdict above. Before Phase 2.4 (or any real traffic), this key needs a paid-tier upgrade (Google AI Studio billing) or a swap to a properly-provisioned key.

## RAG pipeline verified end-to-end with real data (2026-07-26)

The user triggered a real sync from the `/admin/knowledge-base` UI (logged in as an admin in their own browser — this environment has no admin test credentials, so this step could not be done from here). Verified independently afterward via direct DB queries (not just trusting the UI):

- `agent_knowledge_documents`: 3 real rows (2 "E2E Course" test-fixture courses, 1 "Skill Guru" mentor profile), each with a genuine `agent_knowledge_chunks` row carrying a real 768-dimension embedding vector (`vector_dims(embedding) = 768` confirmed via SQL).
- `match_agent_knowledge()` RPC tested directly at the DB level (self-query using a stored chunk's own embedding): returned similarity `1.0` for the two identical E2E-Course chunks and `0.74` for the semantically-related mentor document — correct ranking, confirming the RPC's cosine-similarity search itself works, independent of the application layer.
- A real `converse` call ("Can you tell me about the E2E Course?") correctly: called `knowledge_search`, retrieved the real chunks (similarity ~0.835), set `groundedInKnowledge: true` (correctly, since real sources were used this time — contrast with the earlier empty-corpus test where the same flag was `false` and the model refused to guess), returned a response whose claims ("all experience levels," "completely free") **exactly match** the retrieved chunk content, and did **not** trigger the hallucination-risk override (correct — nothing to override, it was genuinely grounded). Citations (`title`/`category`/`similarity`) were persisted to `agent_messages.citations` and echoed in the API response — confirmed via direct query, not just the API's own claim.

This confirms every stage of the checklist: documents exist → chunks are embedded → the RPC retrieves them correctly → `converse` calls the RPC via the `knowledge_search` tool → retrieved context is injected into the final Gemini pass → the response is honestly grounded in it → citations are surfaced and persisted → the anti-hallucination safeguard correctly stays silent when grounding is real (and fires when it isn't, per the earlier empty-corpus test).
